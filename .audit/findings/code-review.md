## Required

### R-1 — No security headers, and `_headers` cannot protect worker-served pages
**Severity: Required · Security · Effort: S (~30 min)**

Evidence: `public/_headers:1-2` contains only a `Content-Type` rule for `/site-description.jsonld`; the built `out/_headers` is identical (78 bytes). There is no `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `X-Frame-Options`/`frame-ancestors`, `Strict-Transport-Security`, or CSP anywhere. Meanwhile `scripts/generate-markdown.mjs:76` emits a `_routes.json` whose `include` list covers **every page URL** (32 entries for 11 pages — three variants each; generated `out/_routes.json:3-36`), so the new `_worker.js` generates every page response. Cloudflare documents that `_headers` rules **are not applied to responses generated by Pages Functions** ([Cloudflare Pages Headers docs](https://developers.cloudflare.com/pages/configuration/headers/)), which is exactly what this architecture now does for pages.

Why it matters: clickjacking/frame embedding and MIME-sniffing protections are missing on the site's primary surface; the markdown representation is served with a non-HTML `Content-Type` and no `nosniff`; and the project's plan to "harden headers in `_headers`" would silently fail for pages from now on.

Remedy: set a small header block **in the worker** for page responses, and keep `_headers` only for static assets:
```js
const SECURITY = {
  'X-Content-Type-Options': 'nosniff',
  'Referrer-Policy': 'strict-origin-when-cross-origin',
  'Permissions-Policy': 'camera=(), microphone=(), geolocation=()',
  'X-Frame-Options': 'DENY',
}
for (const [k, v] of Object.entries(SECURITY)) response.headers.set(k, v)
```
and in `public/_headers` add `/*` rules for static assets (incl. `/_markdown/*` with `Content-Type: text/markdown; charset=utf-8` and `Cache-Control`). Defer a full CSP: every exported page has 9 inline Next bootstrap scripts plus the inline GA snippet (`out/index.html`), so a CSP needs hashes or `'unsafe-inline'` — do the non-script headers first and treat CSP as a separate decision. Verify HSTS isn't already set zone-wide in Cloudflare before adding it.

### R-2 — GA4 loads unconditionally, including in local dev, with a hard-coded ID
**Severity: Required · Correctness/privacy · Effort: S (~30 min)**

Evidence: `src/app/layout.tsx:70-81` renders the GA loader and inline `gtag('config', …)` on every page in every environment; `src/lib/site.ts:6` hard-codes `GA_MEASUREMENT_ID = 'G-KGS3Q311NR'`. There is no `process.env.NODE_ENV` gate and no consent gate. The project's own plan says the opposite: `SEO_IMPLEMENTATION_PLAN.md:459` "Blocked: Requires an approved GA4 property, measurement ID, and privacy decision"; `:464` "Keep the measurement ID in deployment configuration, not source documentation"; `:467` "Decide whether consent controls are required before enabling analytics."

Why it matters: `npm run dev` now sends pageviews into the production property (analytics pollution that is hard to clean up); the deployment-config decision is violated; and the consent question is unresolved while the tag ships.

Remedy: gate on production and read the ID from config, e.g.
```tsx
{process.env.NODE_ENV === 'production' && (
  <Script src={`https://www.googletagmanager.com/gtag/js?id=${GA_MEASUREMENT_ID}`} strategy="afterInteractive" />
)}
```
with `GA_MEASUREMENT_ID = process.env.NEXT_PUBLIC_GA_MEASUREMENT_ID` (build-time env in Cloudflare Pages), and record the consent decision in the SEO plan.

### R-3 — No site privacy/cookie disclosure for analytics
**Severity: Required · Privacy/compliance · Effort: S–M**

Evidence: the only privacy policy in the app is `src/app/track-my-salah-privacy-policy/page.tsx` — it is explicitly the *Track My Salah app* policy (`:8`, `:18`), is `noindex, follow` (`:10-13`), is excluded from the sitemap (`src/app/sitemap.ts:8-46`), and is linked from no navigation/footer element (grep for `privacy` in `src` returns only that page). GA4 sets `_ga`/`_ga_*` cookies on every page visit (`src/app/layout.tsx:70-81`); there is no consent banner, cookie notice, or site privacy page.

Why it matters: visitors in the EU/UK (and other consent jurisdictions) are served non-essential analytics cookies with no disclosure, no consent, and no linked policy. This is a compliance risk on a public professional site, independent of the code working correctly. (Whether UAE-only operation changes the analysis is an owner/legal question, not a code one.)

Remedy: either (a) add a `/privacy` page describing GA4, cookies, retention and a contact, link it in the footer, and add consent gating for the EEA (a small client component reading `navigator` locale or a geo header), or (b) drop GA4 and use cookie-less Cloudflare Web Analytics, which removes most of the obligation. Document the choice in the plan's Decision log.

### R-4 — Build config is ambiguous/stale: duplicate PostCSS, dead `tailwind.config.js`, redundant `autoprefixer`, broken npm scripts
**Severity: Required · Correctness/maintainability · Effort: S (~30 min)**

Evidence:
- `postcss.config.js:1-6` (CJS, `@tailwindcss/postcss` **+ `autoprefixer`**) and `postcss.config.mjs:1-5` (ESM, `@tailwindcss/postcss` only) both exist. Next/PostCSS resolves a single config (postcss-load-config order puts `postcss.config.js` first), so one file is inert — but which one is active is not obvious to a maintainer. Tailwind v4 does its own vendor prefixing via Lightning CSS, so `autoprefixer` is redundant either way (`package.json:19`).
- `tailwind.config.js:1-96` is never loaded: `src/app/globals.css:1` is plain `@import "tailwindcss";` and no file contains `@config`/`@source`/`@plugin`. Its theme references fonts that no longer exist (`--font-inter`, `--font-playfair`, `--font-caveat` at `tailwind.config.js:11-18`).
- `package.json:10` `"start": "next start"` cannot work with `output: 'export'`; installed Next 16.1.6 throws *"'next start' does not work with 'output: export' configuration"* (`node_modules/next/dist/server/next.js:230`). `package.json:12` `"preview": "npx serve -l 3000 ."` serves the repo root (source, docs, configs), not `out/` — contradicts the correct guidance in `README.md:78`.

Remedy: delete `postcss.config.mjs`, keep one ESM config without autoprefixer, delete `tailwind.config.js`, remove the `autoprefixer` dep, move build tooling to `devDependencies`, delete `start`, change `preview` to `npx serve out -l 3000` (or `npx wrangler pages dev out --port 8788`, which is the only way to exercise the worker). ## Deep dive: markdown-for-agents (new security-adjacent path)

**Verdict: sound.** I traced the request lifecycle and probed the worker with 17 `Accept` cases; the design is small and correct. Specifics:

**Verified good**
- **Path traversal is impossible by construction**: the request path is only ever used as a key (`Object.hasOwn(pages, url.pathname)`, `cloudflare/markdown-worker.mjs:19`), never concatenated into a filesystem/asset path; values come from the build map (`generate-markdown.mjs:69-72`). Prototype-pollution lookup is handled and tested (`tests/markdown-negotiation.test.mjs:75` `/toString`). URL normalization (`..`) can't produce a map hit. The generator writes only paths derived from the build's own output filenames (`generate-markdown.mjs:65-67`).
- **`Accept` parsing behaves correctly** for the cases that matter: case/whitespace tolerance, q-value validation (invalid → 0, max 3 decimals per RFC), explicit `q=0` rejection, wildcards never opt into Markdown (`*/*`, `text/*` → HTML), ties go to Markdown only when Markdown was explicitly requested, and `text/markdown;q=0.0001` correctly beats nothing. Multi-range/duplicate-range headers are handled first-match semantics (fine in practice; see residual note).
- **HEAD is correct** (delegated to the `.md` asset request, validators preserved, no body fabricated); non-GET/HEAD delegates to assets (`:19-21`).
- **`Vary` handling is careful**: appends `Accept` only if absent, treats `*` as already-varying, preserves existing dims (`:34-36`); 304s keep `ETag`/`Vary:*` (tested at `tests/markdown-negotiation.test.mjs:81-98`).
- **Errors are not mislabeled**: `Content-Type: text/markdown` is only set on ok/304 (`:37-39`); a 404 stays `text/plain` (tested).
- **No content-length/body mismatch**: the worker swaps the *request* to the `.md` asset rather than swapping the body of the HTML response, so the returned body and inherited `Content-Length` always describe the same asset (verified by probe: markdown response carried the `.md` length).
- **Homepage `Link` header** is appended, not set, so asset headers survive (tested `:11-21`); generator derives `/site-description.jsonld` from the page's own `WebSite` JSON-LD, so it can't drift (`generate-markdown.mjs:56-62`).
- **Generator fails loudly** on pages missing `<main>` (`:10`) or `<link rel=canonical>` (`:64`), excludes 404/_not-found (`:53`), absolutises links (`:16-19`), fixes heading-link ordering for valid Markdown (`:21-31`), strips nav/footer/scripts/styles/hidden/aria-hidden/empty-alt (`:13`), and the end-to-end test builds a worker in a temp dir and exercises it (`tests/markdown-negotiation.test.mjs:125-150`).

**Residual risks / follow-ups**
1. **Header strategy** — R-1: no security headers on any worker-generated page, and `_headers` cannot supply them.
2. **Cache behaviour is unverified in production.** `Vary: Accept` is correct HTTP, but Cloudflare's edge does not honour all `Vary` dimensions. Pages Functions responses are not cacheable by default and Pages HTML is `max-age=0, must-revalidate`, so I believe poisoning is not exploitable — but this was not verifiable from inside this sandbox (live probes were blocked). Verify once with `curl -sI` in a deployed preview for both representations and confirm no `Cache-Control: public, max-age>0` lands on HTML. If it ever does, keep HTML `no-store`/revalidate.
3. **Duplicate media ranges** (`text/markdown;q=0.2, text/markdown;q=0.9, text/html;q=0.5`) use first-match (`find`) rather than max; RFC 9110 doesn't define this case and real clients don't send it — Nit, not worth fixing unless a parser rewrite happens.
4. **Tests**: add the traversal/encoded-path cases and export `prefersMarkdown` so the behaviour table can be unit-tested directly instead of only through the worker.
